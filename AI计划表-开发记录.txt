【项目概述】
  一个 Windows 桌面应用（Electron），把在 DeepSeek 里规划的计划一键导入，
  AI 自动解析成可打卡、可提醒的任务，支持长达四年的长期计划。
  纯本地运行，数据不上传。

  - 技术栈：Electron 33 + 原生 JS/CSS（无框架）+ DeepSeek API（OpenAI 兼容）
  - 存储：JSON 文件原子持久化，数据在 %APPDATA%\ai-planer\data.json
  - 打包：electron-builder（NSIS 安装包）
  - 许可证：MIT

第 1 阶段：基础应用搭建
--------------------------------------------------------------------------------
需求：
  - 导入 DeepSeek 聊天历史（粘贴 / 文件）
  - AI 解析计划为任务
  - 调度提醒
  - 支持四年长期计划 + 周计划
  - 重复规则、补提醒、开机自启、打开即通知

实现要点：
  - electron/main.js：窗口、系统托盘、系统通知、开机自启、IPC
  - electron/scheduler.js：getOccurrences() 计算每次 occurrence、
    reminderTime()、补提醒（catchUpWindowDays 默认 7 天）
  - electron/store.js：任务存取、JSON 原子写入
  - electron/ai.js：调用 DeepSeek API 解析聊天记录
  - 重复规则：daily / weekly / monthly / yearly，支持 repeatInterval、
    repeatWeekdays、repeatEnds；日期钳制（31 号→月末、2/29→2/28）


--------------------------------------------------------------------------------
第 2 阶段：极简模式（今日视图）与批量管理
--------------------------------------------------------------------------------
需求：
  - 极简模式（今日/today 视图）：2×2 象限布局
  - 每个区域可拖动、拆分、添加/删除、拖拽交换
  - 管理模式编辑区域
  - 「经典模式」改名「编辑计划」
  - 批量管理

实现要点：
  - renderer/app.js：computeLayout()、renderMinimalGrid()、buildColumn()、
    buildPane()、addPane(type)、initSplitters()（拖分隔线）、
    initPaneDragSwap()（长按拖拽交换）、swapSlots()、toggleManage()
  - 区域类型：今日 / 全部 / 未来 N 天 / 已过期（后来去掉「已完成」）
  - 选项卡：今日 / 编辑计划 / 导入 / 设置


--------------------------------------------------------------------------------
第 3 阶段：重复任务「按天完成」语义修复
--------------------------------------------------------------------------------
问题：
  重复任务（每天 + repeatEnds）打勾后整个任务被标记完成，不再提醒，
  「每天刷题」形同虚设。

修复：
  引入「按天完成记录」completionLog（数组，元素 {taskId, dateKey: YYYY-MM-DD}）。
  - 重复任务打勾 = 只标记「今天」完成，明天自动恢复待办
  - 一次性任务打勾 = 整个完成（completed）
  - 渲染层用计算字段 done（今天是否完成）驱动 UI
  - store 新增 isDoneOnDate()、toggleDoneOnDate()、dateKeyOf()
  - scheduler 跳过当天已完成的 occurrence


--------------------------------------------------------------------------------
第 4 阶段：持续任务 + 打卡次数（多次迭代）
--------------------------------------------------------------------------------
（本轮逻辑经过多次澄清，最终确定：持续任务和打卡次数是两个独立概念）

4.1 需求澄清
  用户例子：「10 月 22 号前刷完 1000 题，每天 100 题」
  - 1000 题 ÷ 每天 100 题 = 10 次，但 9 号到 22 号有 13 天
  - 结论：应该设「打卡次数」，在这段时间内打卡 N 次即可，不必每天打

  用户澄清的关键结论（通过提问确认）：
  - 持续任务 = 有明确时间段的任务（期间每天提醒，有「已完成」按钮）
  - 打卡次数 = 独立机制（打卡满 N 次自动完成）
  - 两者可同时存在，也可只有其一
  - 「已完成」按钮 = 整个任务提前完成；截止时间前在今日/全部区域变灰保留
    （激励），未来区域消失
  - 布局：左边 ☑ 打卡方框，中间 ×N 剩余次数，最右边「已完成」按钮

4.2 数据模型新增字段
  - targetCount：目标打卡次数（正整数或 null）
  - isOngoing：持续任务标记（true/false）
  - completionLog 累计得到 doneCount；remaining = targetCount - doneCount
  - finished：打卡满（次数任务 = doneCount >= targetCount；
    时间段任务 = doneCount >= 剩余天数）

4.3 任务类型三选一（编辑任务）
  1. 一次性（repeat=none）
  2. 重复（repeat=daily/weekly/monthly/yearly）
  3. 持续任务（isOngoing=true，repeat 固定 daily，有 repeatEnds）

4.4 打卡交互
  - 今日区域勾 = 打卡/撤销今天（toggleDoneOnDate 今天）
  - 未来/全部区域勾 = 打卡「下一个未打卡日期」（nextUndoneDateKey）
  - 打卡满后不再允许继续勾
  - 完成后：今日/全部区域变灰划线保留（截止前），未来区域消失
  - 未完成的任务排最上面
  - 「已完成」按钮：标记完成（可 toggle 撤销），撤销时弹窗输入剩余量（部分撤销）

4.5 「已完成」按钮文案最终定为
  - 未完成 → 「标记完成」
  - 已完成 → 「已完成 ✓」


--------------------------------------------------------------------------------
第 5 阶段：AI 解析提示词更新
--------------------------------------------------------------------------------
  - 输出格式新增 isOngoing 字段（持续任务标记）
  - targetCount：总量 ÷ 每天进度（如 1000 题 ÷ 100 题 = 10 次）
  - 规则 1（截止时间 + 频率组合）→ repeat + repeatEnds + isOngoing=true
    （+ targetCount 若有总量/进度）
  - 周计划（第 N 周 / 第 N~M 周）→ daily + repeatEnds + isOngoing=true
  - 「持续任务」与「打卡次数」是独立概念，可同时或只有其一

二、关键 Bug 与根因（重要）
================================================================================

1. 打卡后整个任务完成
   根因：completed 是全局布尔，重复任务打勾=整个完成。
   修复：completionLog 按天记录，打勾只标记今天。

2. 打卡后未来/全部区域任务消失
   根因：未来区域用「今天是否完成(done)」过滤。
   修复：未来区域改用「剩余次数>0 / 未完成」判断；打卡后变灰而非消失。

3. 今日打勾导致未来/全部也变灰划线
   根因：三区域共用同一个 done 变灰。
   修复：变灰按区域区分——今日看 done，未来/全部只看 entireDone。

4. 点未来勾撤销了今日的划线
   根因：未来勾也调 toggleDoneOnDate(今天)，toggle 了今天。
   修复：未来/全部勾改调 checkTask，打卡「下一个未打卡日期」。

5. 全部区域无限打勾、不划线
   根因（两处）：
   a) AI 解析的周计划没有 isOngoing 标记，finished 判断失效；
   b) finished 用「总天数(dueAt→repeatEnds)」，但打卡从今天开始，
      过去的天数无法打卡，doneCount 永远到不了总天数。
   修复：
   a) finished 判断不再依赖 isOngoing，只要有 dueAt+repeatEnds 就按时间段算；
   b) finished 用「今天到截止的剩余天数」判断；
   c) nextUndoneDateKey 加上限（打满剩余天数/目标次数后返回 null）。

6. 过了截止时间还能打卡
   根因：nextUndoneDateKey 循环先判断未打卡、后判断截止。
   修复：先判断 cur > end 再判断未打卡。

7. 「已完成」按钮点完变「未完成」反直觉
   修复：文案改为「标记完成」/「已完成 ✓」。

三、核心数据模型（task 字段）
================================================================================
  {
    id, title, description,
    startAt, dueAt, allDay,
    repeat,           // none | daily | weekly | monthly | yearly
    repeatInterval, repeatWeekdays, repeatEnds,
    targetCount,      // 打卡次数（null = 无）
    isOngoing,        // 持续任务标记
    reminderMinutes, completed,
    createdAt, updatedAt
  }
  completionLog: [{ taskId, dateKey(YYYY-MM-DD) }]

  计算字段（渲染层）：
  - done      今天是否打卡（重复任务）或整个完成（一次性）
  - doneCount 累计打卡次数
  - remaining 剩余次数/天数
  - finished  是否打满（自动完成）
  - entireDone = completed || finished

八、需求描述问题分析（供改进参考）
================================================================================
以下是从本次开发中总结的「需求表述」问题点，每条都导致过理解偏差或返工。

【问题 1】同一个词指代多个不同对象
  原文："今日最右边加个已完成选项" / "打卡按钮应该是不能点的" /
        "最右边的已完成按钮呢" / "已完成按钮不是那个能打勾的方框！！！！"
  问题：全程用「已完成」这一个词，去指代至少 4 个不同 UI 元素——
        打卡勾选框、剩余次数标签（×N）、完成按钮、任务状态。
        我多次把「已完成按钮」理解成「打卡」「标签」「勾选框」，来回返工，
        直到最后用感叹号才澄清。
  建议：给每个元素起固定名字，之后始终用同一个名字，例如：
        「打卡勾选框」「剩余次数标签（×N）」「完成按钮」。

【问题 2】两个独立概念先混着说、后拆开
  原文："设个打卡次数……" + "加一个持续任务选项"，
        之后才说"持续任务和次数机制是两个不同的东西"。
  问题：一开始把「持续任务（时间段）」和「打卡次数（N 次）」当一件事说，
        导致我把它们合并实现，后来才澄清是两回事，需要重构。
  建议：涉及多个独立概念时，先一句话说清：
        "有几个概念、各自是什么、彼此什么关系、能不能同时存在。"

【问题 3】规则前后反转
  原文：先"对应次数的最大数字不要超过未来天数"，
        后"最右边是总次数，不受未来天数限制"。
  问题：×N 的显示规则先说要受未来天数限制，后来说不受限制，
        前后矛盾，需要返工。
  建议：一个规则一旦确定，后续修正时明确说"之前那条作废，改成……"。

【问题 4】用结果描述代替机制
  原文："点未来勾，应该让明天的今日区域被划线。"
  问题：这是从"结果"角度描述（明天那条会被划），
        实际机制是"打卡下一个未打卡日期"。
        按结果理解容易实现成"只能打卡明天"，而不是"打卡最近一个未打卡日"。
  建议：尽量描述机制本身："每次点勾 = 打卡下一次"，而不是"让明天划线"。

【问题 5】边界条件散落在多条消息里，未一次说全
  原文："不要让我点了今日的勾，未来的任务就全部消失了" /
        "未来区域全做完的话，还是消失比较好" /
        "截止时间之前变灰保留"。
  问题：完成后的表现（哪里消失、哪里变灰、截止前后怎么变）
        分散在多条消息，且部分互相补充，容易漏实现。
  建议：把"完成任务后的表现"整理成一张表一次说清：
        每个区域 × 每种完成方式（打卡满 / 手动完成 / 过截止）× 表现（消失/变灰/保留）。
